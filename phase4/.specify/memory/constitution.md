# Phase IV Kubernetes Deployment Constitution

## Core Principles

### I. Cloud-Native Correctness

All deployments MUST follow Kubernetes best practices as defined by the official Kubernetes documentation and CNCF guidelines. This includes:
- Proper resource limits and requests defined for all containers
- Health checks (liveness and readiness probes) configured for all pods
- Secrets and ConfigMaps used for configuration (never hardcoded values)
- Services exposed via proper Kubernetes Service objects
- Namespaces used for logical separation where appropriate

**Rationale**: Cloud-native correctness ensures portability, reliability, and maintainability of deployments across environments.

### II. Reproducible Local Deployments

All infrastructure MUST be reproducible on a standard student laptop running Minikube. This means:
- All deployment steps documented with exact commands
- Resource requirements specified and tested on constrained environments
- No reliance on cloud-specific features unavailable in Minikube
- All dependencies (Docker images, Helm charts) version-pinned
- Setup scripts provided for environment initialization

**Rationale**: Reproducibility enables learning, debugging, and validation without cloud infrastructure costs.

### III. AI-First DevOps Automation (NON-NEGOTIABLE)

Manual YAML or Dockerfile writing is PROHIBITED. All infrastructure code MUST be generated using AI tools:
- **Gordon (Docker AI)**: Generate and optimize Dockerfiles
- **kubectl-ai**: Execute Kubernetes operations via natural language
- **Kagent**: Analyze cluster health and optimize resources
- **Helm**: Package applications (AI-assisted chart generation where possible)

**Rationale**: AI-first automation demonstrates modern DevOps practices, reduces human error, and accelerates development.

### IV. Spec-Driven Development Workflow (NON-NEGOTIABLE)

All work MUST follow the Agentic Dev Stack workflow:
1. **Specify** (`/sp.specify`) - Create feature specification
2. **Plan** (`/sp.plan`) - Generate implementation plan
3. **Tasks** (`/sp.tasks`) - Break into TDD tasks
4. **Implement** (`/sp.implement`) - Generate code via Claude Code

No implementation without specification. No code without tasks. No deployment without validation.

**Rationale**: Spec-driven development ensures clarity, traceability, and quality throughout the development lifecycle.

### V. Zero Manual Infrastructure Coding

All production infrastructure code (Dockerfiles, Kubernetes YAML, Helm charts) MUST be generated by Claude Code or AI tools. Manual coding is permitted ONLY for:
- Debugging and investigation (temporary, not committed)
- Documentation and README files
- Configuration of AI tool prompts

**Rationale**: Enforces AI-native engineering practices and demonstrates the power of generative AI in DevOps.

### VI. Observable and Validated Deployments

All deployments MUST be validated before considered complete:
- Pods MUST reach `Running` state
- No `CrashLoopBackOff` or `Error` states permitted
- Services MUST be accessible via browser or API calls
- Logs MUST show healthy application startup
- Resource usage MUST be within defined limits

**Rationale**: Observable and validated deployments prevent silent failures and ensure production-readiness.

### VII. Security-First Configuration

Security MUST be built-in from the start:
- No secrets in Docker images or Git repository
- Kubernetes Secrets or environment variables for sensitive data
- Containers run as non-root users where possible
- JWT tokens and API keys externalized via ConfigMaps/Secrets
- Network policies defined where appropriate

**Rationale**: Security cannot be retrofitted; it must be designed into the architecture from day one.

## Technology Standards

### Required Technology Stack

- **Container Runtime**: Docker Desktop with Gordon AI plugin
- **Orchestration**: Kubernetes via Minikube
- **Package Management**: Helm 3.x
- **AI DevOps Tools**: kubectl-ai, Kagent, Gordon
- **Version Control**: Git with all configurations tracked

### Platform Constraints

- **Local Only**: Minikube cluster (no cloud deployment in this phase)
- **Resource Limits**: Must run on standard student laptop (8GB RAM minimum)
- **Network**: Services exposed via Minikube tunneling or NodePort
- **Storage**: EmptyDir or HostPath volumes (no persistent cloud storage)

### Code Generation Requirements

- All Dockerfiles generated via Gordon with optimization flags
- All Kubernetes manifests generated via Claude Code or kubectl-ai
- All Helm charts initialized via `helm create` with AI-assisted customization
- All deployment commands documented with AI tool invocations

## Quality Gates

### Pre-Deployment Gates

Before any deployment to Minikube:
- [ ] Specification approved and committed
- [ ] Implementation plan reviewed
- [ ] Tasks broken down with acceptance criteria
- [ ] Docker images built successfully
- [ ] Helm charts validated with `helm lint`

### Deployment Validation Gates

After deployment to Minikube:
- [ ] All pods in `Running` state (verify with `kubectl get pods`)
- [ ] All services created (verify with `kubectl get services`)
- [ ] Frontend accessible via browser
- [ ] Backend API responding to health checks
- [ ] Logs show no errors (verify with `kubectl logs`)
- [ ] Resource usage within limits (verify with `kubectl top`)

### Documentation Gates

Before considering phase complete:
- [ ] README with complete setup instructions
- [ ] AI command history documented
- [ ] Troubleshooting section with common issues
- [ ] Verification checklist for instructors
- [ ] Architecture diagram showing components

## Development Workflow

### Phase IV Development Process

1. **Constitution** (`/sp.constitution`) - Define project principles (this document)
2. **Specification** (`/sp.specify`) - Define Kubernetes deployment requirements
3. **Planning** (`/sp.plan`) - Design architecture and approach
4. **Task Breakdown** (`/sp.tasks`) - Create actionable implementation tasks
5. **Implementation** (`/sp.implement`) - Generate infrastructure code
6. **Validation** - Run quality gates and verify deployment
7. **Documentation** - Complete README and guides

### AI Tool Usage Requirements

Every infrastructure operation MUST use AI tools where available:

```bash
# Docker image generation (Gordon)
docker ai "Create optimized Dockerfile for FastAPI backend with Python 3.11"

# Kubernetes operations (kubectl-ai)
kubectl-ai "create deployment for todo-backend with 2 replicas"

# Cluster health analysis (Kagent)
kagent "analyze cluster health and recommend optimizations"

# Helm chart operations
helm create todo-backend
# Then use Claude Code to customize values.yaml and templates/
```

### Commit and Review Process

- All infrastructure code committed with descriptive messages
- AI command history included in commit descriptions
- PHR (Prompt History Records) created for major changes
- ADRs (Architecture Decision Records) for significant architectural choices

## Governance

### Constitution Authority

This constitution supersedes all other development practices for Phase IV. Any deviations MUST be:
1. Documented with clear justification
2. Approved explicitly (recorded in PHR)
3. Time-limited with a remediation plan

### Amendment Process

Constitution amendments require:
1. Documented reasoning for the change
2. Impact analysis on existing work
3. Updated version number following semantic versioning
4. Notification to all stakeholders
