# Data Model: Kubernetes Infrastructure Resources

**Feature**: Local Kubernetes Deployment
**Date**: 2026-01-30
**Purpose**: Document Kubernetes resource entities, relationships, and configuration data

## Overview

This document defines the infrastructure resources (not application data) that comprise the Kubernetes deployment for the Phase III Todo Chatbot application.

## Infrastructure Entities

### 1. Docker Image

**Purpose**: Immutable container image containing application code, dependencies, and runtime environment.

**Attributes**:
- `name`: Image name (e.g., `todo-frontend`, `todo-backend`)
- `tag`: Version identifier (e.g., `v1.0.0`, `latest`)
- `registry`: Image registry location (local Minikube or Docker Hub)
- `size`: Image size in MB (target: <300MB for frontend, <200MB for backend)
- `layers`: Number of image layers (optimized via multi-stage builds)
- `createdAt`: Build timestamp

**Types**:
- **Frontend Image**: Next.js application with Node.js runtime or nginx static server
- **Backend Image**: FastAPI application with Python slim runtime

**Relationships**:
- Referenced by: Kubernetes Deployment (via `spec.template.spec.containers[].image`)
- Built from: Dockerfile (multi-stage)
- Stored in: Minikube local registry or Docker daemon

**Validation Rules**:
- MUST NOT contain hardcoded secrets
- MUST run as non-root user (UID 1000+)
- MUST include health check endpoint
- SHOULD be <500MB total size

**State Transitions**:
```
Building → Built → Pushed → Pulled → Running
```

### 2. Kubernetes Pod

**Purpose**: Smallest deployable unit containing one or more containers. Represents a running instance of the application.

**Attributes**:
- `name`: Pod identifier (generated by Deployment, e.g., `todo-frontend-7d9f8c-abc123`)
- `namespace`: Kubernetes namespace (default: `default` or custom `todo-app`)
- `phase`: Current lifecycle phase (`Pending`, `Running`, `Succeeded`, `Failed`, `Unknown`)
- `conditions`: Health status (PodScheduled, Initialized, ContainersReady, Ready)
- `restartCount`: Number of container restarts
- `startTime`: Pod creation timestamp
- `ip`: Internal cluster IP address
- `node`: Minikube node where pod is scheduled

**Types**:
- **Frontend Pod**: Runs Next.js container serving the web application
- **Backend Pod**: Runs FastAPI container handling API requests

**Relationships**:
- Managed by: Kubernetes Deployment
- Exposes: Container ports (3000 for frontend, 8000 for backend)
- Uses: ConfigMap (environment variables), Secret (sensitive data)
- Accessed via: Kubernetes Service

**Validation Rules**:
- MUST reach `Running` phase within 60 seconds
- MUST pass liveness probe after startup
- MUST pass readiness probe before receiving traffic
- MUST NOT exceed resource limits (memory/CPU)

**State Transitions**:
```
Pending → ContainerCreating → Running → [CrashLoopBackOff if failure]
Running → Terminating → Terminated
```

---

### 3. Kubernetes Deployment

**Purpose**: Manages desired state and scaling of pods. Controls replica count, rolling updates, and rollback.

**Attributes**:
- `name`: Deployment name (e.g., `todo-frontend`, `todo-backend`)
- `namespace`: Kubernetes namespace
- `replicas`: Desired number of pod instances (default: 2)
- `selector`: Label selector matching managed pods
- `strategy`: Update strategy (`RollingUpdate` or `Recreate`)
- `revisionHistoryLimit`: Number of old ReplicaSets to retain (default: 10)
- `progressDeadlineSeconds`: Timeout for rollout progress (default: 600s)

**Types**:
- **Frontend Deployment**: Manages frontend pods with configurable replicas
- **Backend Deployment**: Manages backend pods with configurable replicas

**Relationships**:
- Creates/manages: Pods (via ReplicaSet)
- References: Docker Image, ConfigMap, Secret
- Monitored by: HorizontalPodAutoscaler (optional)

**Validation Rules**:
- MUST define resource requests and limits
- MUST define liveness and readiness probes
- MUST use rolling update strategy for zero-downtime deploys
- SHOULD maintain at least 1 replica during updates (maxUnavailable: 0)

**Configuration**:
```yaml
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```

### 4. Kubernetes Service

**Purpose**: Network abstraction providing stable endpoint for pods. Enables service discovery and load balancing.

**Attributes**:
- `name`: Service name (e.g., `todo-frontend-service`, `todo-backend-service`)
- `namespace`: Kubernetes namespace
- `type`: Service type (`ClusterIP`, `NodePort`, `LoadBalancer`)
- `selector`: Label selector matching target pods
- `ports`: Port mappings (protocol, port, targetPort)
- `clusterIP`: Internal cluster IP (auto-assigned)
- `externalIPs`: External IPs for NodePort type

**Types**:
- **Frontend Service**: NodePort 30080 (external browser access)
  - Type: `NodePort`
  - Port: 80 → targetPort: 3000 → nodePort: 30080
- **Backend Service**: ClusterIP 8000 (internal cluster only)
  - Type: `ClusterIP`
  - Port: 8000 → targetPort: 8000

**Relationships**:
- Routes traffic to: Pods (matched by selector)
- Accessed by: Frontend pods (backend service), External users (frontend service)
- DNS name: `<service-name>.<namespace>.svc.cluster.local`

**Validation Rules**:
- MUST define at least one port
- MUST have selector matching deployment pods
- Frontend service MUST be type NodePort for external access
- Backend service SHOULD be type ClusterIP for security

**Network Flow**:
```
Browser → Minikube IP:30080 → Frontend Service → Frontend Pod:3000
Frontend Pod → backend-service:8000 → Backend Service → Backend Pod:8000
```

### 5. Kubernetes ConfigMap

**Purpose**: Stores non-sensitive configuration data as key-value pairs. Injected into pods as environment variables or volume mounts.

**Attributes**:
- `name`: ConfigMap name (e.g., `todo-frontend-config`, `todo-backend-config`)
- `namespace`: Kubernetes namespace
- `data`: Key-value pairs of configuration (immutable once created)

**Configuration Data**:
- **Frontend ConfigMap**:
  - `NEXT_PUBLIC_API_URL`: Backend API URL (http://backend-service:8000)
  - `NODE_ENV`: Environment mode (production)
- **Backend ConfigMap**:
  - `DATABASE_URL`: SQLite connection string (sqlite:///./todo.db)
  - `LOG_LEVEL`: Logging verbosity (info)

**Relationships**:
- Used by: Deployment (via envFrom or env)
- Mounted as: Environment variables or file volumes

**Validation Rules**:
- MUST NOT contain sensitive data (use Secret instead)
- MUST be created before Deployment referencing it
- SHOULD be immutable (updates require new ConfigMap + rolling deploy)

---

### 6. Kubernetes Secret

**Purpose**: Stores sensitive data (API keys, passwords, tokens) with base64 encoding. More secure than ConfigMap.

**Attributes**:
- `name`: Secret name (e.g., `todo-backend-secrets`)
- `namespace`: Kubernetes namespace
- `type`: Secret type (`Opaque` for generic secrets)
- `data`: Base64-encoded key-value pairs

**Secret Data**:
- **Backend Secrets**:
  - `JWT_SECRET`: Secret key for JWT token signing (base64)
  - `OPENAI_API_KEY`: OpenAI API key for chatbot (base64)

**Relationships**:
- Used by: Deployment (via envFrom or env with secretKeyRef)
- Managed by: Helm chart (values.yaml overrides)

**Validation Rules**:
- MUST be created before Deployment referencing it
- MUST NOT be committed to Git (use .env.example template)
- MUST be base64-encoded in YAML
- SHOULD use RBAC to restrict access

**Security Notes**:
- Secrets are base64-encoded, NOT encrypted by default
- For production: Enable encryption at rest in etcd
- For Minikube: Use external secret management (Sealed Secrets, Vault) for advanced security

---

### 7. Helm Chart

**Purpose**: Package containing Kubernetes manifests and configuration templates. Enables parameterized and reusable deployments.

**Attributes**:
- `name`: Chart name (e.g., `todo-app`, `frontend`, `backend`)
- `version`: Chart version (semver, e.g., `1.0.0`)
- `appVersion`: Application version (e.g., `v1.0.0`)
- `type`: Chart type (`application` or `library`)
- `dependencies`: Sub-chart dependencies

**Chart Structure**:
- **Umbrella Chart** (`todo-app`):
  - Contains sub-charts for frontend and backend
  - Provides global values shared across sub-charts
  - Single `helm install` deploys entire application
- **Frontend Sub-Chart**:
  - Templates: Deployment, Service, ConfigMap
  - Values: Replicas, image tag, resource limits
- **Backend Sub-Chart**:
  - Templates: Deployment, Service, Secret
  - Values: Replicas, image tag, API keys

**Relationships**:
- Contains: Kubernetes resource templates (YAML with Go templating)
- Configured by: values.yaml (default values), user overrides
- Installed as: Helm Release

**Validation Rules**:
- MUST pass `helm lint` without errors
- MUST define all required values in values.yaml
- SHOULD use semantic versioning for chart versions
- SHOULD include NOTES.txt with post-install instructions

## Resource Sizing Guidelines

| Resource | Replicas | CPU Request | CPU Limit | Memory Request | Memory Limit |
|----------|----------|-------------|-----------|----------------|--------------|
| Frontend Pod | 2 | 100m | 500m | 128Mi | 256Mi |
| Backend Pod | 2 | 100m | 1000m | 256Mi | 512Mi |
| **Total** | **4 pods** | **400m** | **3000m** | **768Mi** | **1536Mi** |

**Minikube Cluster Allocation**:
- RAM: 6GB (leaves 2GB for host OS on 8GB laptop)
- CPU: 2 cores
- Driver: Docker (500MB overhead) or VirtualBox (2-3GB overhead)

## State Management

**Stateless Design** (Week 1-2):
- SQLite database stored in emptyDir volume (ephemeral)
- No persistent data across pod restarts
- Suitable for learning and development

**Stateful Upgrade** (Week 3-4, optional):
- PostgreSQL deployment with PersistentVolumeClaim
- Data survives pod restarts
- Backup and restore procedures
- Production-ready pattern

## Notes

- All resources created/managed by Helm (declarative)
- All configurations externalized (no hardcoded values in images)
- All secrets base64-encoded in Kubernetes Secrets
- All resource limits prevent resource exhaustion on Minikube
- All services use label selectors for loose coupling
